# 代码自动化测试 (code_test)

## 适用场景

用户要求为某个 Python 模块或文件生成单元测试、执行测试、统计覆盖率或产出测试报告时，按本流程执行。

## 前置检查

开始前确认：

1. 被测目标路径存在（用 `read_file` 读取，读不到就直接告知用户路径无效，不要继续）。
2. 被测目标确实是 Python 源码（`.py`），不是数据文件或配置。

## 执行步骤（六步闭环）

### 第一步：源码阅读

使用 `read_file` 通读被测模块**及其依赖的接口签名**，明确：

- 每个公开函数的输入类型、输出类型、返回值语义
- 边界条件（空输入、极值、类型边界）
- 异常路径：**什么时候抛异常、什么时候返回错误值**——这两者必须读源码确认，
  不要凭经验假设。本项目里 `read_file` 对不存在的文件返回 `"Error: no such file..."`
  字符串而**不抛异常**，按抛异常写的断言会失败。
- 副作用（文件读写、网络调用、全局状态修改）

**禁止在未读源码的情况下凭空生成用例。** 如果模块依赖了无法读取的外部接口，在报告中明确列出这一限制。

### 第二步：用例生成

用 `write_file` 在 `backend/tests/` 下生成 `test_<模块名>.py`。

要求：

- 覆盖三类场景：**正常路径、边界条件、异常路径**。三类缺一不可。
- 命名与断言风格遵循仓库既有测试约定（若 `backend/tests/` 下已有测试文件，先读取其中一个作为风格参照）。
- 用例名描述行为，不描述实现。用 `test_<函数名>_<场景>_<预期>` 的形式。
- 每个用例只断言一件事。
- 只在必要时构造被测对象，优先依赖被测模块自带的构造函数与工厂函数。
- 断言前先确认被测函数**到底是抛异常还是返回错误值**（见第一步）。

### 第三步 + 第四步：沙箱执行与覆盖率统计

两步由同一条命令完成。通过 `terminal` 执行封装脚本 `airclaw-test`：

```
terminal(
    command="airclaw-test tests/test_<模块名>.py <覆盖率目标>",
    out_dir="backend/reports/<模块名>/<YYYY-MM-DD>/"
)
```

- `out_dir` **必须传**。不传的话输出目录是一次性的，pytest 日志与覆盖率数据会随容器销毁，
  第六步就没东西可归档。
- `<覆盖率目标>` 是被测模块**相对于 `backend/`** 的导入名：被测文件是
  `backend/graph/daily_log.py`，导入名就是 `graph.daily_log`，**不带 `backend.` 前缀**
  （沙箱里的工作目录已经是 `backend/`）。也可以直接给路径 `graph/daily_log.py`。
- 脚本内部已固定好沙箱所需的全部非默认参数（只读工作区、覆盖率数据改道、日志落盘），
  不要自己拼 `python -m pytest` 命令——裸命令在本沙箱里跑不通。

**禁止在宿主机直接运行任何测试代码。**

脚本的 stdout 是**摘要**（退出码、通过/失败数、被测文件覆盖率、失败用例名），
不是完整输出——完整日志太长会被工具层截断，故写进了归档文件。
需要看完整报错时，用 `read_file` 读 `backend/reports/<模块名>/<日期>/pytest.log`。

处理约定：

- 单次执行超时按失败处理，并在报告中记录超时这一事实。
- 资源超限（内存/进程数）同样按失败处理并记录原因。
- 收集阶段出错（退出码 2）说明测试文件本身有问题（导入错误、语法错误），
  先修测试文件再重跑，不要继续往下走。
- **不要为了让测试通过而修改被测代码。**

### 第五步：报告生成

汇总摘要、`pytest.log` 与 `coverage.json`（都在归档目录里，用 `read_file` 读），
**用 `write_file`** 写出 Markdown 报告到 `backend/reports/<模块名>/<日期>/report.md`。

不要试图用 `python_repl` 写文件——它在沙箱内执行，输出目录是一次性的，写出来的东西
随容器销毁。需要计算时可以让 `python_repl` 把结果 print 出来，再由你写进报告。

报告**必须**包含：

| 章节 | 内容 |
| --- | --- |
| 测试概览 | 用例总数、通过数、失败数、通过率、总耗时 |
| 覆盖率 | 行覆盖率、分支覆盖率、未覆盖行号 |
| 失败用例明细 | 用例名、预期、实际、原始报错、初步原因分析 |
| 测试环境 | 沙箱镜像、Python 版本、pytest 版本、执行时间 |
| 限制与说明 | 未能覆盖的部分及其原因（如依赖了不可用的外部接口） |

### 第六步：归档

归档目录就是第三步 `out_dir` 指定的那个，已在逐步写入：

```
backend/reports/{模块名}/{YYYY-MM-DD}/
├── test_<模块名>.py    # 测试用例副本，由 airclaw-test 自动复制
├── pytest.log          # pytest 完整执行日志，由 airclaw-test 写入
├── coverage.json       # 覆盖率原始数据，由 airclaw-test 写入
└── report.md           # 测试报告，由你在第五步写入
```

收尾时用 `read_file` 确认目录里这几样都在，再向用户报告归档路径。

## 迭代上限（重要）

测试写完不通过是常态，但要给自己设上限，否则会陷进反复调试：

- 同一类失败**最多修两轮**。两轮之后仍不通过就按「测试失败」收尾：如实报告失败
  用例、原始报错与初步原因分析，把报告写出来，不要继续改。
- 判断依据是「改了用例之后，失败原因是否变了」。若连续两轮都是同一个断言在同一处
  失败，说明你对被测行为的假设还没搞对——回去重读源码，而不是继续调断言。
- **不要为了让用例通过而放宽断言或删掉用例。** 该失败就让它失败，在报告里写清楚。
  一份"全绿"但什么都没验证的报告，比一份如实记录失败的报告有害得多。

用例数量上，单一模块通常 5～12 个就够覆盖正常/边界/异常三类场景。堆到几十个既超出
需求，也更容易引入基于错误假设的用例。

## 输出物清单

- [ ] `test_<模块名>.py` 测试用例文件（`backend/tests/`）
- [ ] pytest 执行日志（归档目录）
- [ ] coverage 覆盖率数据（归档目录）
- [ ] 测试报告 `report.md`（归档目录）

## 安全边界（重要）

1. **严禁修改被测业务代码。** 测试失败时，只做缺陷现象记录与初步定位分析。
2. 如需修复，**仅允许输出修改建议**，由研发人员人工确认后另行执行。
3. 所有执行动作在 Docker 沙箱内完成，宿主机不得直接运行 Agent 生成的任何指令。
4. 归档目录内的文件不得包含被测代码中的敏感内容；如被测代码本身敏感，停止技能执行并提示用户。

## 失败处理

| 情况 | 处理 |
| --- | --- |
| 无法读取被测源码 | 停止，告知用户路径无效或权限不足 |
| 收集阶段出错（退出码 2） | 修测试文件（导入名、路径、语法），重跑，不进入后续步骤 |
| pytest 执行超时 | 按失败处理，报告中记录超时与已产生的部分输出 |
| 覆盖率数据为空 | 检查覆盖率目标写对没有；仍为空则在报告中标注"未统计"及原因 |
| 测试用例生成失败 | 停止，说明卡在哪一步，不产出半成品报告 |
